# VZip 设计

## 场景

固定机位拍小孩朗读：背景几乎不动、主体是人脸和嘴、信息全在人声、平台只显示到 720p、上传有硬上限（超 1KB 也失败）、使用者是家长。

→ 时间冗余极大，降帧率收益高；音频不能压狠；必须"目标体积驱动"而非"目标画质驱动"。

## 选型

- **编解码复用 ffmpeg**。Rust 生态无成熟解码/封装方案（rav1e 只编码且慢，openh264 仅 H.264 编码），自研不划算。Rust 的价值在编排层。
- **子进程调 CLI**，不用 ffmpeg-next FFI。FFI 需要 ffmpeg dev 库且版本必须匹配（9.0 对应 7.x，本机 5.1.9 编不过）、各平台链接麻烦、分发要带一堆动态库、静态编译要 10~30 分钟 + GPL 传染 + 每平台 CI。CLI 无编译期依赖、版本随便换。
  执行层抽象成 `Encoder` trait，将来换 FFI 只改一个文件。
- **GUI 用 egui**（M1）。界面只有四个控件（拖放区 / 上限输入 / 进度条 / 结果提示），用不上 HTML/CSS 的表现力；egui 换来单条 Rust 工具链、单文件产物、用户零运行时依赖。
  **唯一额外成本**：egui 默认字体不含中文，必须加载中文字体。
  **换成 Tauri 2 的触发条件**：要在界面里内嵌播放视频（压前预览 / 压后对比）——egui 做不到，Tauri 一个 `<video>` 标签就行。

## ffmpeg 定位

按序查找，找到即停：

1. `--ffmpeg` 显式指定 / `VZIP_FFMPEG` 环境变量
2. PATH 中的 `ffmpeg`（系统安装的）
3. exe 同目录（便于绿色版/便携版）
4. **打包自带的二进制**（资源目录，随安装包分发）

**必须自带**：Windows / macOS 没有预装 ffmpeg，不带就是开箱即用不了。Linux 优先用系统的。

分发时带**精简静态构建**（只留 h264/hevc + aac + mp4/mov 的 demux/mux），约 20~40MB/平台，比完整版 70~100MB 小很多。

找到后：校验主版本 ≥ 4.4；用 `ffmpeg -encoders` 做能力探测（不同构建带的编码器不同，不能假设 x264 一定在）。全部找不到 → 友好提示 + 让用户手动指定路径。

## 架构

```
vzip-core
  resolve  定位 ffmpeg/ffprobe + 版本/能力探测
  probe    ffprobe JSON → 时长/分辨率/帧率/旋转/码率
  plan     目标体积 → 码率预算 → 分辨率/帧率阶梯（bpp 判据）
  encode   拼参数、两遍 ABR、-progress 解析、可取消
  lib      编排：编码 → 校验 → 降级重试
vzip-cli → vzip-gui
```

## 压缩策略

### 预算

```
视频预算 = 目标字节 × 8 ÷ 时长 − 音频码率(96k 单声道)
         × 0.97   ← 安全边际（容器头 + 编码器浮动）
```

音频固定 AAC 96kbps 单声道（人声足够，比手机默认 256k 立体声省 2~4 倍）。

**码率封顶**：预算过宽时（30 秒视频算出 5Mbps）不要用满，取 `min(预算, 原片码率×0.8)`。填满只会更大更慢。

### 选档：bpp

`bpp = 视频码率 ÷ (宽 × 高 × 帧率)`。H.264 + 头肩朗读这类低运动画面：

≥0.10 宽松 ｜ **0.05~0.10 良好（目标）** ｜ 0.03~0.05 可接受 ｜ <0.03 糊

长边阶梯 1920 → 1280 → 960 → 854，帧率 30 → 24 → 20，取第一个 bpp ≥ 0.05 的组合；都不满足取最低档。降帧率等于每帧多一倍码率，对静态画面性价比最高。

### 两遍 ABR

pass 1 扫全片分析帧复杂度（`-pass 1 -an -f null -`，不产出文件），pass 2 按统计精分配码率。体积命中 ±5%（CRF 是"要画质"，体积不可控），同体积画质更好。耗时约 1.5~1.8 倍。

### 降级与地板

用户要求：压不到目标就压到极值，**不报错**。补充约定：**不静默失败**（家长以为压好了、上传照样失败更糟），且有质量地板（压成糊片等于没帮上忙）。

```
0. 初始档
1. 码率 ×0.90      2. 帧率 30→24      3. 长边→1280
4. 码率 ×0.85      5. 长边→960        6. 帧率 24→20
7. 长边→854   ← 地板，停止
```

地板：长边 ≥ 854（480p）、帧率 ≥ 20、bpp ≥ 0.02。

```rust
pub struct CompressResult {
    pub output: PathBuf,
    pub size_bytes: u64,
    pub target_bytes: u64,
    pub target_met: bool,      // 达标
    pub reached_floor: bool,   // 撞到质量下限
    pub attempts: u32,
}
```

撞地板时给出路，不是只说不行：① 剪片头片尾（省约 20%）② 拆两段 ③ 放宽上限。M0 只给文字建议。

预计 90%+ 第 0 档就命中，不会走到降级。

### 预设：M0 不做

固定 CRF 档位保证不了体积（同样 720p CRF23：30 秒 3MB，10 分钟 200MB），所以引擎统一走"目标体积驱动"。

M0 只提供一个入口 **`--max-size 20MB`**，直接由用户指定上限，不引入任何平台相关概念（微信 / 钉钉 / 学校平台）。

平台档位（`--preset`）和配置文件后续需要时再加，届时数值以用户配置为准，不写死在代码或文档里。

## 坑

1. **旋转 metadata**：手机竖拍常带 `rotate=90`，不处理压出来是躺倒的。用 `-noautorotate` 关掉自动旋转，再自己按探测结果加 `transpose` 滤镜，确定性最高
2. **许可证**：分发含 x264/x265 的 ffmpeg 涉及 GPL/LGPL。子进程调用比静态链接传染风险低一个量级；上架/商用需单独评估
3. **硬件编码**：本机有 `/dev/dri`、无 NVIDIA。M0 只用软件 libx264，接口留着；硬件编码器（NVENC/VideoToolbox 跑在独立芯片）不占 CPU，届时并发才有意义
4. **并发默认串行**：libx264 内部已吃满所有核，再开多进程只会总耗时不变、内存翻倍。参数默认 1，M0 不实现
5. **egui 中文字体**：默认字体不含 CJK，必须显式加载（约十几行代码 + 几 MB 字体，或用自动探测系统字体的库），否则界面全是方框

## 里程碑

- **M0** 单文件 CLI：`vzip in.mp4 --max-size 20MB`，含旋转、进度、两遍编码、校验降级、结果报告
- **M1** GUI（egui）：拖拽 + 填上限 + 进度条 + 结果提示。**顺带做每平台打包并自带精简 ffmpeg**——Windows / macOS 没预装 ffmpeg，不带就是双击没反应
- **M2** 引擎增强：预设 + 批量 + 硬件编码回退 + 取样试压（先压 8~10% 中段估算，重试从 2~3 次降到 1 次）+ 剪片头片尾
